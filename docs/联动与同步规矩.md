# 三库联动与同步规矩

三个库各管一件事，谁都不能越界写别人的内容。这份文档是规矩本身。

## 一、职责

| 库 | 管什么 | 唯一源头 |
|---|---|---|
| `local-experience-kb` | 设计、规范、决策、一致性清单 | 是（概念与契约） |
| `local-experience-kb-mvp` | 核心实现：存储、检索、面板、MCP | 是（代码源头） |
| `dsh-plugin-local-kb` | DSH 适配器：工具、挂件、索引注入 | 是（适配层） |

**核心代码只有一份源头**：`local-experience-kb-mvp` 的 `src/`、`web/`。
插件里的 `lib/kb/`、`lib/web/` 是**打包副本**，由同步脚本生成，不手改。

## 二、互链规则

每个仓库的 README **顶部必须有另外两个库的链接**，缺一个算不合格：

| 仓库 | 必须链到 |
|---|---|
| 骨架 | MVP、插件 |
| MVP | 骨架、插件 |
| 插件 | 骨架、MVP |

链接放在第一屏，不埋在文末。

## 三、改哪、怎么同步

### 改设计/规范

1. 改骨架文档；
2. 如果影响接口：升 `docs/规范/MCP工具契约.md` 的 `specVersion`；
3. 更新一致性清单；
4. 推骨架。

### 改核心代码

1. 改 `local-experience-kb-mvp` 的 `src/` 或 `web/`；
2. 跑测试：`node --test test/`（本机）；
3. 同步副本：`node _工具/sync-plugin-lib.mjs`；
4. 检查：`node _工具/sync-plugin-lib.mjs --check` 必须输出"一致"；
5. 先推核心，再推插件（插件依赖新的核心行为）。

### 改插件

1. 只改 `dsh-plugin-local-kb` 里的 `index.mjs`、`widget.js`、`cordis.patch.yml`、`README.md`；
2. **不要改 `lib/`**——它是副本，改了下次同步会被覆盖；
3. 如果确实需要改核心行为，回"改核心代码"流程。

### 改完必做

```
node _工具/sync-plugin-lib.mjs --check     # 副本一致
node _工具/check-three.mjs                  # 三处互链存在
```

两条都过，才能推。

## 四、版本与发布

| 库 | 版本方式 |
|---|---|
| 骨架 | 不设版本，按文档日期/决策编号 |
| 核心 | 语义化 `0.x.y`，接口变升次版本 |
| 插件 | 跟随自己的发布节奏，不和核心锁死 |

### 只往前发，不移动旧 tag

每次发布都按顺序做，**tag 建了就不改**：

1. 改 `package.json` 的 `version`（修复 → patch，如 `0.1.0` → `0.1.1`；新增能力 → minor）；
2. 跑测试和审计：
   ```
   node 测试/run-checks.mjs
   node _工具/sync-plugin-lib.mjs --check
   node _工具/audit-repos.mjs
   ```
3. 提交并推送；
4. 打与 `version` 同名的 tag，写 release notes（这次修了什么、有什么限制）；
5. 核对 tag 指向的提交与 `package.json` 版本一致。

**禁止**：`git tag -f`、强推 tag、把旧 tag 挪到新提交。打错了就补一个 patch 版本，让历史保持可追溯。

> 2026-11-08 之前移过一次 tag（`v0.1.0`/`v0.14.0`），那是前期迭代的特例；从此不再这样做。

### 版本和代码对不上时

以 `package.json` 为准；release notes 里写清对应提交和日期。

## 五、禁止

- 不直接改插件 `lib/` 里的文件；
- 不在三个仓库各写一份规范（规范只在骨架）；
- 不把插件的安装说明复制进核心 README（只放链接）；
- 不在 README 里写"代码暂时不公开"这类会过期的状态；
- 不移动已发布的 tag。

## 六、长期目标

插件最终改成**依赖核心包**（GitHub dependency），删掉 `lib/` 副本；那时同步脚本可以退役。
在那之前，副本 + 检查脚本就是规矩的执行手段。
